# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Expo SDK version notice

This project targets **Expo SDK 57**, which changed significantly from prior versions. Read the versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing any code that touches Expo APIs, config, or routing.

## What this app is

A hair-regrowth treatment tracker: log daily AM/PM doses, keep an angle-matched photo timeline, and see consistency stats — jargon-free, non-punishing tone (never guilt-inducing copy, streaks freeze rather than reset during a pause). **v1 is fully local-first — no backend, no auth.** All data lives on-device in SQLite; a sync/auth layer may be layered on later, which is why local IDs are UUIDs shaped like they'd already work as remote primary keys.

## Commands

```bash
npm install            # install dependencies
npm run start           # start the Expo dev server (expo start)
npm run ios             # start dev server and open iOS simulator
npm run android          # start dev server and open Android emulator
npm run web             # start dev server for web (see Known limitation below)
npm run lint            # expo lint (ESLint via eslint-config-expo)
npm test                # jest (jest-expo preset)
npx tsc --noEmit         # type-check the project
npm run db:generate      # regenerate src/db/migrations/ after editing src/db/schema.ts
npm run reset-project     # moves current app/ to app-example/ and creates a blank app/ (irreversible without git)
```

`expo-env.d.ts`, `.expo/`, and the typed-routes declarations (`.expo/types/router.d.ts`) are generated on first `expo start` and are gitignored — if `tsc` complains about missing `expo/types` or an unrecognized route string passed to `router.push`/`href`, run `npx expo start` once (even briefly, Ctrl-C after it says "Waiting on...") to regenerate them.

**No data-changing schema migration has ever shipped yet** — the single migration in `src/db/migrations/` has never reached a real user, so when the schema changes, delete `src/db/migrations/` and run `npm run db:generate` fresh rather than adding a second migration. Once this ships, switch to always adding a new migration instead.

## Architecture

### Routing & onboarding gate
- Entry point is `expo-router/entry`; routes live under `src/app/` (not the default `app/`).
- `src/app/_layout.tsx` is the only place that runs DB migrations (`useMigrations` from `drizzle-orm/expo-sqlite/migrator`) and sets up `QueryClientProvider` + `ThemeProvider`. It renders a **bare** `<Stack screenOptions={{ headerShown: false }} />` — no `<Stack.Screen>` children.
- **Never add `<Stack.Screen name="..." options={{...}}>` children to the root `<Stack>`.** This previously hung the entire app on boot on a real Android device via Expo Go (SDK 57) — confirmed by root-causing with trace logging: the root layout, migrations, and `DoseNotificationResponder` all rendered and completed fine, but React Navigation never invoked the initial route's component at all (no crash, no error, just silent — the JS thread stayed responsive to native events like the dev-menu shake gesture the whole time). Declaring ~10 explicit children (mixing route groups and deeply-nested leaf routes) is what triggered it; a fully bare `<Stack />` booted correctly. Root cause is presumed to be inside `expo-router`'s/React Navigation's native-stack screen registration for that Expo Go build, not our code — but the fix is simple and must stay: every screen that wants a header/title sets it itself via an inline `<Stack.Screen options={{...}} />` as the first child of its own return (see `consistency.tsx`, `timeline.tsx`, `export.tsx`, `treatment/start-new.tsx`, `treatment/start-new-custom.tsx`, `treatment/confirm.tsx`, `photos/capture.tsx`, `photos/compare.tsx`, `learn/[articleId].tsx` for the pattern — the last one is also the reason this pattern was already proven safe before the fix). If you're tempted to consolidate header options back into the root layout for tidiness, don't — test on-device first if you do.
- `src/app/index.tsx` is the gate: it queries whether a `profiles` row exists and `<Redirect>`s to `/(onboarding)/welcome` or `/(tabs)`. It also runs the missed-dose reconciliation pass (see below) once per cold start before hiding the splash screen.
- Onboarding is a fixed linear flow under `src/app/(onboarding)/`: `welcome → profile → treatment-select [→ treatment-custom] → reminder-times → baseline-photos`. Draft state across these screens (name, age, chosen drugs, reminder times) lives in a Zustand store (`src/features/onboarding/draft-store.ts`) and is only persisted to SQLite on the final "Finish" tap in `baseline-photos.tsx` — that one screen creates the profile, the first treatment period, app settings, and schedules notifications, then routes to `/(tabs)`. "Start New Treatment" (`src/app/treatment/`) is the same preset-or-custom-then-confirm shape as onboarding but as its own draft store (`start-new-draft-store.ts`) and its own routes, since it commits directly rather than gating on a profile existing.
- Adding a new route file requires regenerating typed routes before `tsc` will recognize it in `router.push`/`href`/`<Link>` — see the `expo start` note below. This trips people up constantly on this project; check it first if `tsc` rejects a route string you just added.
- Path aliases (`tsconfig.json`): `@/*` → `src/*`, `@/assets/*` → `assets/*`.

### Local data layer
- `src/db/schema.ts` is the drizzle-orm SQLite schema — source of truth for the data model. Edit it, then `npm run db:generate` to produce a new migration in `src/db/migrations/`.
- `src/db/client.ts` opens the SQLite DB (`expo-sqlite`) and wraps it with drizzle. It's constructed at module scope — fine on native, but see the web limitation below.
- Core tables: `profiles` (single row), `treatmentPeriods`, `treatmentPeriodDrugs` (a period can bundle multiple drugs, e.g. Dut+Min+Fin), `treatmentPausePeriods` (a period can be paused/resumed multiple times — each cycle is its own row so the Timeline can render every pause as a distinct segment), `doseLogs` (one row per AM/PM slot per day, unique on `(treatmentPeriodId, date, slot)`), `photos` (each linked to the `treatmentPeriodId` active when captured — that link, not a date-range recomputation, is what the compare screen uses to flag "treatment changed in between"), `appSettings` (single row: reminder times, notifications on/off, `lastPhotoSetDate`).

### The bug that cost a day: bounded loops
`computeCurrentStreak` walks *backwards* day by day from today. Dates before the first treatment period resolve to `no-treatment`, and the loop was written to **skip** those (so a pause doesn't break a streak) rather than stop — so it only ever terminated on an `incomplete` day. For any user without one (e.g. someone who logged every dose as taken), it walked into the infinite past: verified reaching **the year 1479** before a guard tripped.

That's a synchronous infinite loop inside a React Query `queryFn` on the JS thread, so it presented as: a **totally black, completely unresponsive app** — no error, no red screen, nothing in the Metro logs beyond the last successful render, unaffected by cache clears or a full phone restart. It looked exactly like a native mounting failure, and ~a day was lost bisecting navigation code before the real cause was found. Every unit test passed the whole time, because every fixture happened to include an `incomplete` day.

Lessons that apply to anything added here:
- **Any backwards/unbounded walk over dates needs an explicit lower bound.** `computeCurrentStreak` now takes `earliestDate` as a *required* third argument (the first period's start date, or `null` for no history) precisely so the compiler forces every call site to supply one — don't make it optional.
- When the app freezes with clean JS logs, **suspect a synchronous loop in the code that runs right after the last log**, not the renderer.
- Tests over hand-written fixtures prove the cases you thought of. `streak.test.ts`'s `computeCurrentStreak termination` block covers the "no `incomplete` day anywhere" shapes specifically — keep those.

### Dose tracking domain logic
This is the part of the app most worth understanding before touching it — it's pure, unit-tested, and everything else (Home screen, Consistency/streak stats, notification scheduling) is built on top of it.
- `src/features/dose-log/doseState.ts` — pure functions, no I/O: `getRequiredSlots` (which AM/PM slots were actually required on a date, given treatment period history + pause windows), `resolveDayStatus` (rolls a day's slots into `no-treatment | in-progress | complete | incomplete`), `computeEffectiveState` (a stale unresolved `pending` row from a past day reads as `missed` **without needing a background job** — see reconciliation below), `computeRepromptTime` (the "No" response 6-hour reprompt, dropped if it would land outside 10:00–24:00 or cross midnight).
- `src/features/consistency/streak.ts` — `computeCurrentStreak`, `computeBestStreak`, `computeMonthRatio`, `computeSlotBreakdown`, all built on `resolveDayStatus`. Key behavior: a paused/no-treatment day is skipped (neutral), not treated as a break — pausing freezes the streak instead of punishing it. An in-progress "today" doesn't zero out yesterday's streak.
- `src/features/dose-log/doseState.test.ts` and `src/features/consistency/streak.test.ts` cover the non-obvious edge cases (pause freezing, in-progress-today, the reprompt window). Run these first after touching either file.
- `src/features/dose-log/api.ts` is the SQLite-backed layer: `logDose` (Taken/Skipped — locks immediately), `recordDoseNoResponse` (stays unlocked so it can still resolve to Taken), `reconcileMissedDoses(fromDate)` — walks forward from a date and persists `missed` for any unresolved slot before today. This runs once per app launch from `src/app/index.tsx` instead of a server-side cron, since there's no backend.
- `src/features/consistency/hooks.ts`'s `loadConsistencyContext` builds one `DayStatusResolver` (plus a `requiredSlotsFor`/`effectiveStateFor` pair and the earliest treatment start date) from all dose logs/periods/pauses — the shared foundation for both `useConsistencyStats` (current streak, best streak, month ratio, AM/PM breakdown, the heatmap's day-status map, backing `src/app/consistency.tsx`) and the export feature's PDF summary (see Export below). Reuse it rather than re-querying the DB if you need day-status data outside a React component.
- The Consistency heatmap doubles as the PRD §4.2 "corrections" affordance: tapping a day opens `DayDetailCard` (`src/features/consistency/components/day-detail-card.tsx`), which shows that day's slots and lets a Missed one (still unlocked) be marked Taken retroactively via the same `useLogDose` mutation Home uses. It resolves the *period* for that date via `findPeriodForDate`/`getPeriodForDate` (`treatment/api.ts`) rather than assuming the currently active period, since a past date can fall under one that's since ended.
- `src/features/timeline/build-timeline.ts` is a pure merge-and-sort of treatment-period starts, pause/resume events, and photo-capture dates into one feed (unit tested) — backs `src/app/timeline.tsx`, pushed from the Routine tab.

### Notifications
- **`expo-notifications` must never be statically imported** (`import ... from 'expo-notifications'`) anywhere in this codebase — on Android inside Expo Go, just importing it throws at module-evaluation time (a push-token auto-registration side effect in the package's own entry file, unrelated to whether push tokens are used — this app only uses local scheduled notifications, never push), which crashes the entire app bundle before any of our code runs. `src/lib/notifications-safe.ts`'s `getNotificationsModule()` loads it lazily via `require()` inside a function, guarded by `isRunningInExpoGo() && Platform.OS === 'android'`, returning `null` in that one environment so every caller can no-op instead of crashing. Every function in `notifications.ts` and `notification-responder.tsx` goes through this — if you add a new one, do the same (`const Notifications = getNotificationsModule(); if (!Notifications) return;`). This only affects Expo Go specifically; a real dev/production build doesn't hit it.
- `src/lib/notifications.ts` schedules local daily AM/PM reminders (`expo-notifications`, no push server) for whichever slots the active treatment requires, tagged with a `dose-response` notification category carrying Yes/No/Skip action buttons. Called from onboarding's finish step and Start New Treatment's confirm step; re-call `rescheduleDailyReminders` whenever the regimen changes.
- `src/features/dose-log/notification-responder.tsx` (`<DoseNotificationResponder />`, mounted once in the root layout) handles the action button taps: Yes/Skip call `logDose` and lock immediately; No calls `recordDoseNoResponse` and, if `computeRepromptTime` returns a time, schedules a one-off reprompt (`scheduleReprompt`) that reuses the same category. A body tap (not a button) is a no-op — it just opens the app.
- `schedulePhotoReminder`/`cancelPhotoReminder` handle the separate "every 15 days" photo prompt (PRD §4.3/§5.4) — a one-off `DATE`-triggered notification, not the `DAILY` type the dose reminders use, always rescheduled forward from `computeNextPhotoReminderDate(lastPhotoSetDate, intervalDays)` (`src/features/photos/photo-reminder.ts`, pure/tested) via `recordPhotoSetCompleted`. Home's banner (`isPhotoReminderDue`, same file) is the in-app half of the same prompt — it's deliberately independent of `getRequiredSlots`/pause status, since photo reminders continue by default even while dosing is paused (PRD §5.5).

### Photos
- `src/features/photos/api.ts`: `savePhoto`/`captureCurrentPhoto` copy the picked/captured image into app-managed storage under `Paths.document/progress-photos/` (files must be copied out of the picker's temp location or they can vanish) before inserting the DB row; `getPhotosByAngle` backs the compare screen. `recordPhotoSetCompleted` is the single place that both stamps `appSettings.lastPhotoSetDate` and reschedules the 15-day photo reminder (see Notifications) — call it (not `setLastPhotoSetDate` directly) whenever a full angle set finishes.
- The `Directory`/`File` instances are constructed lazily inside functions, not at module scope — `expo-file-system` has no native module during `expo start --web`'s SSR pass (plain Node), so a module-scope `new Directory(...)` crashes the whole route tree at import time. If you add a new file-system call here, keep that pattern.
- `src/features/photos/components/angle-capture-flow.tsx` (`AngleCaptureFlow`) is the shared 4-angle grid used by both onboarding's baseline photos and the standalone "Add photos" flow — it owns the captured-photos state and swaps to a full-screen `GuidedCamera` (`guided-camera.tsx`, wraps `expo-camera`'s `CameraView`) when an angle is tapped, with a `GuidedCameraOverlay` (`guided-camera-overlay.tsx`) drawing a simple dashed outline + label per angle and a "choose from library" fallback for simulators/no camera permission. The two screens differ only in header copy, save-button label, and what `onSave` does with the result (`footer` is a render-prop so onboarding's "Skip for now" link can see the live captured-photos state).
- `src/features/photos/components/comparison-slider.tsx` is a real drag-to-reveal slider (`react-native-gesture-handler` + `reanimated`), not a static side-by-side.
- `src/app/photos/compare.tsx`'s quick-picks ("Day 0 vs Today", "Last Month vs Today") use `findClosestPhoto` (`src/features/photos/quick-pick.ts`, unit tested) to find the nearest photo to a target date within the chosen angle.
- **Simplification vs PRD §5.4**: the on-screen guide is plain dashed shapes, not real silhouette artwork — that needs actual design assets, not more code.

### Export
- `src/features/export/resolve-range.ts` (`resolveExportRange`, pure/tested) turns a range option (`last-month | last-3-months | all-time | custom`) into concrete from/to dates. `all-time` falls back to today if there's no treatment history yet.
- `src/features/export/build-pdf.ts` (`buildExportHtml`, pure) renders the HTML that `expo-print` turns into a PDF — image `src`s are the photos' local `file://` paths directly (works fine in `expo-print`'s WebView on native; would need base64 conversion if this ever needs to work in a browser context).
- `src/features/export/api.ts` (`generateAndShareExport`) is the I/O glue: reuses `loadConsistencyContext` (see Dose tracking domain logic below) plus `computeRangeRatio`/`computeCurrentStreak`/`computeBestStreak`, generates the file via `Print.printToFileAsync`, hands it off via `expo-sharing`.

### Learn
- Static content in `src/features/learn/content/` (`articles.ts`, `faq.ts`) — plain data, no CMS. `searchLearnContent` (`src/features/learn/search.ts`, pure/tested) is a simple case-insensitive substring filter over both.
- Article detail (`src/app/learn/[articleId].tsx`) is the one route whose header title is set inline via `<Stack.Screen options={{title:...}}/>` rather than in the root layout, since the title is dynamic.

### What's built vs. simplified
Every PRD v1 screen and flow exists: onboarding, Home (core loop + the 15-day photo banner), Routine (current treatment, pause/resume, Start New Treatment, Timeline), Consistency (streak/ratio/breakdown stats, heatmap, tap-a-day corrections), Photos (guided capture/grid/compare), Learn, Me (reminders, notifications toggle, PDF export). What's *not* PRD-complete: the capture guide is dashed shapes, not real silhouette artwork (see Photos above); Learn's content is a real but not exhaustive first pass. Verified booting and navigable on a real Android device via Expo Go (SDK 57) — see the root-Stack note, the tab bar note, and the Link/asChild rule above for three on-device-only bugs that only real hardware surfaced (none reproduced in any simulator/emulator, because none was available here — treat "no simulator to test on" as a real gap, not a substitute for a device); web remains broken (see below).

### Theming & UI primitives
- `Colors`, `Fonts`, `Spacing`, `BottomTabInset`, `MaxContentWidth` live in `src/constants/theme.ts` — use these tokens instead of hardcoding values in `StyleSheet.create`. Dose-state colors (`taken`, `missed` — the latter used for both Skipped and Missed, since the PRD treats them identically in the UI) are also there.
- **Never pass an array `style` prop (`style={[a, b]}`) to the direct child of `<Link asChild>`.** `Link`'s `Slot` clones that child and throws — not a warning, a render-crashing error on-device — if its `style` isn't a flat object. Always `StyleSheet.flatten([...])` first. This broke the Photos and Learn screens once already; if you add a new `<Link asChild>` usage with more than one style source, flatten it up front. (This project no longer uses `expo-router/ui` at all — see the Tabs note below — so this only applies to `Link`.)
- **Always build time-of-day inputs with `TimePickerField`** (`src/components/time-picker-field.tsx`), never a raw `<DateTimePicker mode="time">`. `@react-native-community/datetimepicker` renders inline on iOS but is dialog-only on Android — an unconditionally-mounted one pops up as a clock dialog the instant the screen renders, with no tap needed (this broke Me and onboarding's reminder-times once already). `TimePickerField` handles the per-platform difference: iOS stays inline; Android shows a tappable label and only mounts the dialog on tap. Date pickers (`mode="date"`, e.g. `treatment/confirm.tsx`, `export.tsx`) don't need this — they're already conditionally shown via a `pickerTarget`-style state, which is the same fix applied by hand.
- `useTheme()` (`src/hooks/use-theme.ts`) returns the resolved `Colors[light|dark]` object. `ThemedText`/`ThemedView` (`src/components/`) read from it so screens shouldn't need manual light/dark branching.
- **The tab bar is the standard `<Tabs>` from `'expo-router'`** (React Navigation's bottom-tabs), replacing an earlier custom bar built on `expo-router/ui`'s headless `Tabs`/`TabList`/`TabTrigger`/`TabSlot`. The standard one gives a native tab bar with safe-area handling built in, and avoids the `Slot`/`asChild` array-style footgun the custom one kept hitting. (The switch was originally made while chasing a freeze that turned out to be [the streak infinite loop](#the-bug-that-cost-a-day-bounded-loops) — `expo-router/ui` was **not** at fault and worked fine on-device; the standard API is kept because it's simpler, not because the other one was broken.) `src/app/(tabs)/_layout.tsx` renders a bare `<Tabs screenOptions={{...}} />` and each of the 5 tab screens sets its own `title`/`tabBarIcon` via an inline `<Tabs.Screen options={{...}} />` (icons via `expo-symbols`' `SymbolView`). If a screen has multiple `return` branches (loading/empty/loaded), the `<Tabs.Screen>` must be in *every* branch — see `(tabs)/index.tsx`'s `HomeTabScreen` helper.
- No styling library (no NativeWind/Tamagui/Unistyles) — plain `StyleSheet.create` plus the theme tokens.

### Known limitation: web + expo-sqlite (confirmed upstream bug, not a config issue)
`expo-sqlite`'s web backend runs SQLite compiled to WASM inside a Worker, synchronized with the main thread via `SharedArrayBuffer`/`Atomics`. `npm run web` reliably throws `Sync operation timeout` from `src/db/client.ts`'s `openDatabaseSync(...)` call — reproduced both in a sandboxed headless-Chromium session and in a real, normal desktop Chrome, so this is not an environment artifact.

Root-caused via Playwright instrumentation (worker script and `.wasm` both load fine, `crossOriginIsolated`/`SharedArrayBuffer` are both true, COOP/COEP headers in `metro.config.js` are working — the worker itself just never responds before the sync-wait spin loop times out) and cross-checked against [expo/expo#36392](https://github.com/expo/expo/issues/36392) and its fix, [expo/expo#36669](https://github.com/expo/expo/pull/36669): the underlying cause is that **expo-sqlite's synchronous API (`openDatabaseSync`, which `drizzle-orm/expo-sqlite` is built on — there's no async variant of that driver) doesn't work reliably on web**, per Expo's own maintainers in that PR. #36669 fixed the kv-store's sync path specifically; the direct `openDatabaseSync` path this project uses still hits it.

There is no cheap fix — switching web to a working state would mean bypassing drizzle's typed query builder on web in favor of raw SQL over `openDatabaseAsync`, which is a real rearchitecture, not a config tweak. Given the actual target platform is native (iOS/Android, where `expo-sqlite` uses the real native SQLite binding — no WASM/Worker/OPFS involved, so none of this applies), that tradeoff isn't worth it unless web support becomes a real product requirement. Don't re-debug this without a specific reason to prioritize web.
